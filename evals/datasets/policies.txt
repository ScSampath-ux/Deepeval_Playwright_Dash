
### 1. Unable to Select the Saturday Delivery Option
**Problem**
The Saturday Delivery option cannot be selected while processing a shipment.

**Cause**
The Saturday Delivery option is available only when the Saturday Delivery feature is enabled in the Admin Profile Options, and a FedEx service that supports Saturday Delivery is selected.

**Solution**
1. Enable Saturday Delivery in Admin Profile Options.
2. Select a FedEx service that supports Saturday Delivery.
3. Retry the shipment.

**Expected Result**
Once the feature is enabled and a supported FedEx service is selected, the Saturday Delivery option becomes available for selection.

**Keywords**
Saturday Delivery, Saturday Shipment, FedEx, Admin Profile Options, Shipping Page

**Additional Notes**
Module: Shipping
Category: Configuration

• Saturday Delivery option is disabled.

### 22. Error While Dispatching – Shipconsole Integration with Oracle
**Problem**
When attempting to dispatch a shipment from Oracle, the process fails with the message: “Error while dispatching.”
This occurs during the integration between Oracle and ShipConsole, when shipment data is sent from Oracle (via Oracle Integration Cloud – OIC) to ShipConsole’s ShipAPI for label generation and shipment confirmation. In this scenario, the shipment remains partially processed or hung in Oracle, and no shipping label is generated.

**Cause**
This error occurs when the data sent from Oracle to ShipConsole’s API contains invalid or missing values.
In this specific case:
• The field `packageSequence`, which should contain a numeric value (e.g., 1, 2, 3), had an empty or non-numeric value in the OIC request payload.
• ShipConsole’s API validates all incoming fields and rejected the request as invalid, returning a HTTP 400 (Bad Request) error.
• Because of this, the dispatch process in Oracle failed and the shipment remained in an incomplete state.

Example from OIC log:
`shipments[3].packageInfo[0].packageSequence: packageSequence should be numeric`

**Solution**
1. **Verify Shipment Data in Oracle**: Check the shipment and package details for the affected batch or delivery. Ensure that each package has a valid numeric `packageSequence`, and all mandatory fields such as weight, dimensions, and freight terms are properly entered.
2. **Review OIC Logs**: Open the OIC integration instance for the failed dispatch call. Review the request payload sent to ShipConsole’s ShipAPI. Confirm whether any field (especially `packageSequence`) is blank, null, or non-numeric.
3. **Correct Invalid Data**: Update the incorrect shipment or package details in Oracle. If the shipment is stuck in a partially processed or hung state, have your Oracle team reset the record via SQL update to clear the partial transaction.
4. **Reprocess the Shipment**: Once data corrections are made, retry dispatch from Oracle. The shipment should process successfully and generate a shipping label from ShipConsole.
5. **Prevent Future Occurrences**: Ensure the integration mapping between Oracle and OIC always passes numeric values for `packageSequence`. Validate data before invoking ShipConsole’s API to avoid dispatch failures.

**Expected Result**
The shipment processes successfully and generates a shipping label from ShipConsole after data corrections and clearing partial transactions in Oracle.

**Keywords**
Error while dispatching, 400 Bad Request, package Sequence should be numeric, invalid data, Ship API, dispatch failed, Oracle Integration Cloud, UPS, partial shipment, Shipconsole

**Additional Notes**

### 23. Batch Ship Confirm Not Working for a Single Delivery
**Problem**
When performing a Batch Ship Confirm in ShipConsole, one or more deliveries may not get ship confirmed in Oracle, even though other deliveries in the batch process successfully. In some cases, users may manually ship confirm the same delivery in Oracle later and it works fine.

**Cause**
This issue occurs when Oracle prevents updates to certain shipment attributes — specifically, the Confirmed Date attributes on the delivery record.
During Batch Ship Confirm, ShipConsole sends a request to Oracle to update the confirmed date and status. If the “Confirmed Date” attributes are disabled for update in Oracle, the API call from ShipConsole fails with an Oracle error such as:
`Error: You can't update these Confirmed Date attributes for the <delivery_number> shipment because they're disabled.`
As a result:
• The ShipConsole batch process marks the delivery as processed,
• But Oracle rejects the update,
• So the delivery remains unconfirmed in Oracle.
This usually impacts only specific deliveries, depending on their setup or data conditions in Oracle.

**Solution**
1. **Verify in Oracle**: Check whether the affected delivery is already ship confirmed (manually or via another process). If not, review the delivery attributes in Oracle and ensure that the Confirmed Date fields are enabled for update.
2. **Check for Attribute Restrictions**: In Oracle, navigate to the Delivery form or Shipping Transaction form. Review the Confirmed Date and Actual Departure Date attributes. If these are disabled (greyed out or locked), Oracle will not allow updates from any external system — including ShipConsole.
3. **Reprocess the Delivery**: Once the Confirmed Date attributes are enabled, reattempt the Batch Ship Confirm for the same delivery. The delivery should now confirm successfully in Oracle.
4. **If Urgent**: If the delivery needs immediate processing, you can manually ship confirm the specific delivery in Oracle as a temporary workaround. Then recheck your Oracle setup to prevent this from happening again.

**Expected Result**
The delivery confirms successfully in Oracle during Batch Ship Confirm once Confirmed Date attributes are enabled for update in Oracle.

**Keywords**
Batch Ship Confirm, single delivery failed, Confirmed Date disabled, Oracle update restriction, ShipConsole, delivery not confirmed, error while batch confirm, intermittent batch confirm issue

**Additional Notes**
• This issue is delivery-specific, not a general batch failure.
• ShipConsole is functioning correctly — it sends the update, but Oracle rejects it due to configuration restrictions.
• To avoid future occurrences: Ensure that Confirmed Date attributes are not locked or restricted for update; periodically verify delivery attribute settings in Oracle if batch confirmations intermittently fail.

   • If shipment is exempt from AES filing: Enter your FTR Exemption Number in the field labeled FTR Exemption Number (e.g. `NOEEI 30.36` or `30.37`).
3. **Save and Retry**: Click Save on the International Details screen, then re-process the shipment.

**Expected Result**
The shipment completes successfully and shipping labels print as expected.

### 32. Error in Shipping – UPS Token Expiry or Missing Service Level
**Problem**
When processing a UPS shipment in ShipConsole, users may see an error message like “Error in Shipping.”
This issue usually occurs when:
• The UPS tokens used for communication with UPS have expired, or
• The service level is missing in the carrier configuration or ship method mapping.

**Cause**
1. **Expired UPS Tokens**: ShipConsole uses access tokens to communicate securely with UPS. The access token expires every 4 hours, and the refresh token expires every 60 days (1440 hours). If token renewal fails (for example, due to a temporary UPS API issue), shipments may fail with an “Error in Shipping.”
2. **Missing Service Level Configuration**: If the UPS service level (like “Ground” or “Next Day Air”) is not mapped correctly in the carrier configuration or ship method mapping, ShipConsole cannot send the correct shipment request.

**Solution**
1. **Verify UPS Token Validity**: Ask your IT or ShipConsole admin to generate and load new UPS tokens by running the token update script provided by ShipConsole Support. Once tokens are loaded, retry processing the shipment.
2. **Revalidate Carrier Configuration**: Go to Carrier Configuration in ShipConsole Admin. Select Operating Unit, Organization, and UPS Carrier. Click Go to retrieve details, then click Save to reapply settings. Open Ship Method Mapping, review the methods, and click Save again. Retry shipment.
3. **Confirm Label Format**: If label prints as junk characters, your setup is using ZPL (thermal) label format. Use a Zebra ZPL printer for such labels. To print on plain paper, change the Label Format in Carrier Configuration to PDF, then reprocess and print using View Label.

**Expected Result**
Shipments process successfully without token or service level errors, and labels print correctly in the designated format.

**Keywords**
Error in Shipping, UPS Token Expiry, Missing Service Level, UPS Ground, Carrier Configuration, Ship Method Mapping, ZPL Label, PDF Label, Token Refresh, UPS API Error, Label Printing Issue

**Additional Notes**
• Access Token Validity: 4 hours.
• Refresh Token Validity: 60 days (1440 hours).
• ShipConsole automatically refreshes tokens, but if the UPS API is temporarily unavailable, manual token load may be needed.

### 34. UPS Labels Not Printing – Error “lp: Too Many Active Jobs”

2. **Restart Print Spooler Service**: Restart the print spooler service on the server where the printer is installed.
3. **Test Printing from ShipConsole**: Go to ShipConsole → Shipments, retrieve a shipment, click View Label or Print Label, and verify printing.

**Expected Result**
Print spooler queue clears, allowing ShipConsole print commands to reach the thermal printer successfully.

**Keywords**
UPS label not printing, lp too many active jobs, print spooler error, ShipConsole printer issue, label not generated, UPS shipment success no label, FAB_UPS_SC_Z, KDS_UPS_SC, OS print queue, UPS carrier configuration, printing failure
